# 0002. 麻雀の対局イベントを、イベントを正として保存し Pub/Sub で配信する

- ステータス: 提案中
- 日付: 2026-11-11

## コンテキスト

麻雀の対局中に起きる操作（ツモ・打牌・鳴きなど）をイベントとして扱い、次の 2 つに使いたい。

- **牌譜の保存**: 対局を後から再生・分析できるようにする。
- **観戦者へのリアルタイム配信**: 観戦者に対局の進行を届ける。観戦者には全員の手牌とツモ牌を見せてよい。

要件は次のとおり。

- イベントの範囲は、局の開始（配牌）・ツモ・打牌・鳴き・リーチ・和了・流局・局の終了。
- 局の中のイベントの順序は必ず守る。
- 配信の遅延はできる範囲で小さくする（厳密な上限は決めない）。
- 実行環境は Google Cloud。インフラは Terraform で管理する。

操作はプレイヤーのクライアントが API を呼んで行う。API は手番・合法かどうか（その牌を持っているか、鳴けるか）・鳴きとロンの優先順位を判定するため、局の状態を DB に持つ必要がある。

このとき、1 回の操作で「DB に書く」と「Pub/Sub に発行する」の 2 つが起き、片方だけ成功する場合がある（二重書き込みの問題）。

- DB に書けたが発行に失敗すると、牌譜が欠け、配信も止まる。
- 順序キー付きの発行は、一度失敗すると同じキーの後続の発行が止まる（Node.js のクライアントでは `resumePublishing()` を呼ぶまで再開しない）。

## 決定

### イベントを正とする（イベントソーシング）

- 対局のイベントを DB（Cloud SQL for PostgreSQL）のイベントのテーブルに追記する。これを正とし、局の状態はイベントから組み立てる。
- イベントのテーブルには `(局 ID, 通し番号)` の一意制約をかける。
  - 局の中の順序がこの通し番号で決まる。
  - 鳴きとロンのように操作が同時に来たときは、同じ通し番号への追記がぶつかるので検出できる。後から来た側は局の状態を組み立て直して判定し直す。
- イベントのテーブルがそのまま牌譜になる。

### 発行

- API は、イベントのコミット直後にそのイベントを Pub/Sub に発行する（遅延を小さくするため）。
- 別にリレーを用意し、発行済みの記録がないイベントを通し番号の順に発行し直す（取りこぼしを防ぐため）。
- 順序キーは局 ID とし、サブスクリプションで順序指定を有効にする。

### 購読

1 つのトピックから、用途ごとにサブスクリプションを分ける。

- **観戦配信**: イベントを受け取り、WebSocket または SSE で観戦者に届ける（Cloud Run）。
- **牌譜の転送**: 分析用の保存先（例: BigQuery）に送る。

共通のルールは次のとおり。

- Pub/Sub は「少なくとも 1 回」の配信で、さらにコミット直後の発行とリレーの両方から同じイベントが届くことがある。購読側は `eventId`（または局 ID と通し番号）で重複を除くか、処理を冪等にする。
- 通し番号が飛んだら欠けとみなし、イベントのテーブルから取り直す。
- 一定回数失敗したメッセージは Dead Letter トピックに移す。

### インフラ

トピック・サブスクリプション・Dead Letter トピック・IAM（発行・購読のサービスアカウント、Push 型の OIDC 認証）は Terraform で管理する。

### パッケージ

| パッケージ | 種類 | 役割 |
| --- | --- | --- |
| `packages/mahjong` | コアドメイン | 麻雀のドメイン（牌・役・局・対局の進行）。ルールとゲームを分けるかは、実装を進めながら決める |
| `packages/mahjong-game-event` | イベントの契約 | 発行・購読するイベントのスキーマ。発行する側と購読する側がこれだけを共有する |
| `packages/mahjong-game-api` | API | 操作を受け付けて、イベントを追記・発行する。リレーも置く |
| `packages/mahjong-spectator` | API | 観戦配信。後で作る |
| `infra/` | Terraform | トピック・サブスクリプション・IAM など |

- 公開するイベントはインターフェースとして扱う。`mahjong-game-event` は `mahjong` に依存させず、牌なども文字列（例: `"5m"`、赤は `"5mr"`）のような単純な形で表す。
  - ドメインの中のイベント（`mahjong`）は、局の状態を組み立てるためのもので、自由に形を変えてよい。
  - 公開するイベント（`mahjong-game-event`）は購読する側との約束で、変えるときはバージョンを上げて互換性を保つ。
  - 両者の変換は `mahjong-game-api` の `adapter/out/messaging` で行う。
- 既存の `mahjong-api` の麻雀のドメイン（役・点数申告など）も、将来は `packages/mahjong` で共通に持つ。ただし移すのは `mahjong-api` の移行を計画するときとし、まずは対局のために `packages/mahjong` を作る。

## 影響

### よくなること

- 発行に失敗してもリレーが拾うので、牌譜も配信も欠けない。
- 局の中の順序が DB の一意制約で決まり、発行・購読でも同じ順序を使える。
- 牌譜を別に組み立てる必要がない。
- 操作がぶつかったときの扱い（鳴きとロンなど）を、一意制約の違反として統一して扱える。

### 注意すること

- 局の状態をイベントから組み立てる処理が必要になる。1 局は多くても数百イベントなので、性能上は問題にならない見込み。
- リレーという常駐または定期実行の処理が増える。
- 購読側は、重複と欠けを前提に作る必要がある。
- Pub/Sub エミュレーターでは確かめられない機能（exactly-once 配信、IAM、Push の認証など）があり、本物の環境での確認が必要。
- 観戦者には全員の手牌がリアルタイムで見えるため、対局中のプレイヤーが観戦画面でほかの人の手牌を見られる。必要なら配信を遅らせるなどの対策を別途検討する。

## 検討した代替案

- **DB に書いてすぐ発行する（失敗は許容する）。** 最も簡単で遅延も小さいが、発行に失敗すると牌譜が欠け、順序キーの発行が止まる。順序が必須の要件に合わない。
- **Transactional Outbox（局の状態はテーブルで持つ）。** 取りこぼしも順序も守れるが、局の状態とイベントを別々に持つことになる。牌譜はイベントの列そのものなので、イベントを正としたほうが二重に持たずに済む。
